## 1. 提案の結論

PROSPECT.mdの6項目を次期開発の対象候補にする。機能追加・二言語文書・公開準備を順に進め、Marketplace公開は最後に独立した判断として扱う。

最優先の条件は、項目1「同じタブでプレビュー」を実現するために現行機能を削らないこと。現時点で機能削除が必要だと判明したわけではない。現行の標準プレビュー、読み取り専用仮想ファイル、成功結果の保持を継続し、表示位置と元入力への復帰だけを追加する方式を第一候補とする。

ただし、**同じエディター領域で入力とプレビューを切り替えること**と、**入力のタブそのものをプレビューへ置換してタブを1枚にすること**は区別する。前者は現行方式で実現できる見込みがある。後者の成立は未確認であり、前者だけを実装して「同じタブを達成」とは報告しない。

次の工程は、この違いと機能保持を確認する小規模検証である。今回は資料・コード・公式仕様の読取と設計案の作成までとし、検証用コードも作成していない。

## 4. R1: 同じタブ／領域でのプレビュー

### 4.1 事実と見込み

現行src/open-preview.cjsは、結果URIと標準Markdownカスタムエディター種別を照合して既存タブを探し、あればそのグループを再利用する。ない場合だけ横に開く。src/preview.cjsは生成Markdownを読み取り専用の仮想ファイルとして保持し、表示時に変換JavaScriptを実行しない。

VS Codeの公開コマンドvscode.openWithは、表示するリソース、エディター種別、表示オプションを受け取る。表示オプションには表示グループを指定できる。[V1][V2]

確認した公式1.105.1のshowPreview.tsでは、通常のmarkdown.showPreviewは元エディターの列、横表示はBesideを指定する。公式の説明もCtrl+Shift+Vによる表示切替と横表示を区別している。[V3][V4]

以上から、現在の固定型プレビューを同じ領域に表示する案は成立する見込みがある。ただし、表示列の指定は入力タブそのものの置換保証ではない。現行製品への変更・GUI試験は未実施である。

### 4.2 選択肢と推奨

| 案 | 使用感 | 現行機能への影響 | 判断案 |
|---|---|---|---|
| A: 同じ領域内で標準プレビューへ切替 | 横分割せず結果を表示。元入力タブを保持し、コマンドで戻る | 変換・保存・画像代理読込の仕組みを維持できる見込み | 第一候補。タブが1枚になるとは約束しない |
| B: 入力タブ自体を置換 | 見かけのタブを1枚にする | 入力URIと結果URIが異なる。未保存編集、Undo、タブ位置・復帰・状態の維持を別途確認する必要がある | 無損失で成立する場合だけ採用候補。未確認 |
| C: 独自プレビューへ移行 | 表示を独自制御できる | 標準プレビューとの互換性や保守負担が変わる | 今回は採用しない |

「同じタブ」の採用基準はN1の結果を見て決める。案Aをユーザーの承認済み解釈とは扱わない。案Bのために元文書を保存・破棄したり、機能を省いたりする方式は採用しない。

### 4.3 操作案

- 現行の5コマンドと既存キー割当は維持する。従来の横表示も使えるようにする。
- 新しい「入力と結果を切り替える」操作と、独立した「元の入力へ戻る」コマンドを追加する。
- 指定キーは、Ctrl+Shift+Alt+Vを押して離し、Vを押す2段階の入力として解釈する。キー定義候補は `ctrl+shift+alt+v v`。同時押し1回へ読み替えない。[V5]
- 切替時にその入力の成功結果があれば、保持済みの結果を表示する。単なる表示切替では再変換しない。
- 成功結果がなければ、処理を選んで実行する案内を表示する。その明示操作で選択・実行し、成功後に同じ領域へ表示する。取消・初回失敗では空の成功結果を作らない。
- 更新は既存の再実行コマンドを使う。既存の「前回」はワークスペース内の最後の成功した組という意味を維持する。表示中の別入力に合わせて勝手に変更しない。
- プレビューから戻る先は、そのプレビューに対応する元入力とする。単に「最後の成功入力」を使うと、複数結果を表示したときに誤復帰するので区別する。
- 対象外タブや端末にはこのショートカットを効かせない。標準Ctrl+Shift+Vとユーザー設定を変更しない。

### 4.4 状態と復帰の設計候補

生成結果のURIと元入力URIの対応を管理する。入力から切り替える際には元のグループ、選択範囲・カーソル、表示位置を記録し、戻る際に可能な範囲で復元する。元文書を保存・再作成・強制クローズしない。文書のUndoと未保存内容はその文書に保持させる。

同一結果のプレビューが別グループに存在する場合は、重複を増やさず同じ領域へ移せるかをN1で確認する。安全な移動と既存再利用を両立できない場合は、その差異を報告して採否を戻す。別グループを表示しただけで同じ領域の要件を満たしたとはしない。

再起動後に復元する成功結果は現行どおり最後の1件とする。セッション中の入力別結果と最後の成功組を混同しない。再起動後は旧タブの参照を再利用せず、現存タブを探し直す。カーソル等の補助情報がない場合は元入力を開く基本動作を成立させ、位置まで復元できたとは報告しない。

元入力の移動・削除、ルートの除去、元グループの消失では、復帰失敗の理由を示してプレビューと結果を保持する。代わりの入力を名前から推測しない。VS Code標準の「ソースを表示」は生成Markdownを対象とする可能性があるため、元のYAML等への復帰は本拡張のコマンドで明示する。

### 4.5 機能を削らないための採用条件

| 維持対象 | 必須条件 |
|---|---|
| 標準Markdownプレビュー | 標準レンダリングを維持し、独自レンダラーへ変更しない |
| 完全手動変換 | 保存・自動保存・言語設定変更・表示切替で勝手に再実行しない |
| 変換契約 | 4拡張子、CommonJS／ESM、非同期、利用側npm、保存済みJSの次回反映を維持する |
| 入力の扱い | 未保存編集を実行時に読む。元入力・変換JSを保存・破棄・書換えしない |
| 結果保持 | 失敗・中断・状態保存失敗で前回成功結果と組を保持する |
| タブ管理 | 対象URIを取り違えず、再表示・再実行・移動後も不要な重複を作らない |
| 復帰 | 正しい入力へ戻り、未保存内容とUndoを失わない |
| 画像・リンク | 現行対応範囲の同じフォルダ以下の画像と読取リンクを維持する |
| 永続化 | 最後の成功結果を再起動後に変換なしで復元する |
| 安全性・制御 | 信頼確認、排他、Workerの実停止、出力・ログ上限を維持する |

**いずれかを削る必要が判明したらR1の採用判断を停止し、失われる機能・原因・代替案を提示する。ユーザーが再判断するまで、削減版を実装しない。** 項目2〜5を先行する場合も、次の実行指示で範囲を明示する。

## 5. R2: .cjsテンプレート作成

テンプレートの内容は、現行のidentityサンプルと同じくtextをそのまま返す最小の非同期関数とする。YAML解析、業務用整形、npm導入は追加しない。

| 場面 | 動作案 |
|---|---|
| 入力が開いている | その入力のワークスペースルートとtransformsFolderを作成先候補にする |
| 入力がない／複数ルート | ルートを明示的に選ぶ。別ルートを勝手に使用しない |
| ワークスペースなし | フォルダを開く案内で終了する |
| 作成先フォルダなし | 選択したルート内であることを確認し、作成先を示して作成する |
| ファイル名 | 例: identity.cjs。利用者が変更可能。直下の.cjsとして扱える名前に限定する |
| 同名ファイルあり | 上書きしない。別名または取消を選ぶ。既存ファイル自体は変更しない |
| 作成成功 | UTF-8で新規作成し、内容確認後に編集画面を開く。作成だけで変換しない |
| 作成後の候補 | 次の選択実行で見つかる。再ビルド・再インストール不要 |
| 未信頼 | 初期案は作成を停止して理由を案内する。既存結果の再表示は妨げない |

配布物内の実テンプレートを標準の取得元にする。これが欠落した場合は、同じ最小内容を内蔵した予備から作成できる案とする。予備を使ったことを知らせ、ファイルと予備の内容一致・配布物への収録を検証する。欠損を理由にネットワークからコードを取得しない。

利用者が作成済みの変換.cjsを失った場合は別問題として扱う。再実行時は現行どおり消失を通知して結果を保持し、勝手にidentityへ置き換えない。作成コマンドで雛形を新規作成できても、利用者の独自処理を復元したとは説明しない。

実装時はパス逸脱、symlinkによる外部への書込み、作成時の名前衝突を確認する。新規作成専用の書込みを使い、確認後に他の処理が同名ファイルを作っても上書きしない。

## 6. R3: 機能の英語・日本語対応

設定案は `markdownPreviewViaJsTransforms.language`、値はauto／en／ja、初期値auto。autoはVS Codeの表示言語に従い、日本語以外では英語へフォールバックする。利用者単位の設定とし、入力ファイルごとにUIの言語が変わらないようにする。

対象はコマンド名、候補選択画面、情報・エラー通知、進捗、テンプレート案内、本拡張が生成する診断メッセージ。ユーザーJavaScriptのconsole出力、例外原文・スタック、ファイルパス、識別子、コード、生成Markdownは翻訳しない。診断には安定した識別情報を残す。

### 公式方式の制約と対応案

package.nls.jsonとpackage.nls.ja.jsonはmanifestの静的な表示を翻訳する公式方式で、選ばれる言語はVS Code側のlocaleに基づく。[V6] したがって、この2ファイルを置くだけで拡張独自のlanguage設定に従うとは説明できない。

| 対象 | 方式案 | 判断 |
|---|---|---|
| 実行時の案内文 | 本拡張の設定から辞書を選ぶ。設定変更後、次の表示から反映 | 直接制御する |
| コマンドパレットのコマンド名 | 英語・日本語の表示用入口を用意し、条件付きで片方だけを表示。内部処理は共通化 | 第一候補。N1で実動確認する |
| 既存コマンドID | 現行IDの登録と動作を維持。表示用入口が共通処理を呼ぶ | 利用者のキー割当・既存呼出しを壊さない |
| manifestの設定説明等 | 公式package.nls方式によるVS Code表示言語への追従 | 拡張独自の切替とは適用範囲を分けて記載する |
| VS Code本体のUI | 本体の言語設定に従う | 本拡張では書き換えない |

条件付きコマンド表示は公式contributes.menus.commandPaletteとwhen条件を使う候補である。[V7][V8] 起動直後にコマンドが消える問題、両言語の重複、最近使ったコマンドの残留、ショートカット表示・検索・キー割当画面への影響を検証する。未検証の方式を確定採用しない。

PROSPECT.mdの「右側の文」は、まずコマンド名の表示部分を意味するものとして扱う設計案とする。補助表示・元言語の別名・ショートカット欄などVS Code側が生成する部分まで含むかは、N1の画面比較で示す。制御できない箇所があれば未達として明示し、案内文だけの翻訳で要件を満たしたことにしない。

独自言語切替が安定しなければ、「すべてVS Code表示言語に従う」という簡易案も比較する。ただしこれは原項目3の条件変更なので、自動採用しない。

## 8. R6: Marketplaceの準備と公開の境界
